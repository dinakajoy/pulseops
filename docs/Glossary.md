# Glossary
This glossary defines the business terminology used throughout the PulseOps project. It establishes a shared vocabulary for Product, Engineering, QA, and other stakeholders to ensure consistent communication and understanding.

| **Term**               | **Definition**                                                                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **Organization**       | A SaaS company that subscribes to and uses PulseOps to manage operational incidents (your customer).                                            |
| **Project**            | A logical grouping of related services and operational resources that are managed together.                                                     |
| **Service**            | A deployable software component or system that delivers a specific business capability, such as the Authentication API or Notification Service. |
| **Tenant**             | A customer organization using the SaaS product operated by a PulseOps customer.                                                                 |
| **Affected Tenant**    | A tenant whose use of the SaaS product is impacted by an incident.                                                                              |
| **Customer Report**    | A complaint or issue reported by a tenant regarding the SaaS product.                                                                           |
| **Client**             | An end user of the SaaS product.                                                                                                                |
| **Incident**           | An unplanned event that disrupts or degrades the normal operation of one or more services.                                                      |
| **Incident Manager**   | The user responsible for coordinating the overall response to an incident.                                                                      |
| **Responder**          | A user assigned responsibility for investigating and resolving an incident.                                                                     |
| **Root Cause**         | The underlying reason an incident occurred.                                                                                                     |
| **Severity**           | The business impact level assigned to an incident (e.g., Critical, High, Medium, Low).                                                          |
| **Timeline Event**     | A recorded activity or status change that occurs during the lifecycle of an incident.                                                           |
| **Status**             | The current state of an incident (e.g., Open, Investigating, Resolved, Closed).                                                                 |
| **Resolution**         | The documented explanation of how an incident was resolved and its final outcome.                                                               |
| **Investigation Note** | Technical findings, observations, or progress updates recorded by engineers during an incident investigation.                                   |
| **Corrective Action**  | A task or change implemented to prevent an incident from recurring.                                                                             |
| **Audit Log**          | A record of significant actions performed by users within the system.                                                                           |
| **Attachment**         | A file associated with an incident, such as screenshots, log files, or other supporting evidence.                                               |
